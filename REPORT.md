## Remote, слияние и восстановление

DVC remote `storage` — папка `../dvc-remote-tarancenko` относительно репозитория.
В `.dvc/config` путь записан относительно `.dvc`: `../../dvc-remote-tarancenko`.
Все четыре версии отправлены командой `dvc push`. CSV и cache в Git отсутствуют.

Ветки `feature/wine` и `feature/iris-features` созданы от одной базы.
Перед созданием второй ветки выполнен `dvc checkout`: Wine исчез, Iris вернулся к базе.
При одном `git switch` данные ещё оставались прежними, а `dvc status` показывал изменение `data`.

В ветке признаков выполнено слияние `feature/wine` через DVC merge driver.
Драйвер автоматически объединил состояния директории, маркеров конфликта нет.
После `dvc checkout` и проверки данных merge сохранён и включён в `main`.
У merge-коммита два родителя: история обеих веток сохранилась.

Чистый клон: `../mlops-data-tarancenko-clean`.
До `dvc pull` в нём не было `data` и `.dvc/cache`.
Из remote получены оба итоговых CSV; их SHA-256, формы и столбцы совпали с исходным репозиторием.
В этом же клоне из remote восстановлены и проверены `data-v1`, `data-v1.1` и `data-v2`.
Для `data-v1`, созданного до настройки remote, адрес задан отдельно в `.dvc/config.local`.
Старые workspace и cache вручную не копировались. Клон оставлен на `main`.

Итог: `dvc status` — без изменений, `dvc status --cloud` — данные синхронизированы.

## Демонстрационный ноутбук

Выполнены все 14 ячеек кода; ClearML-ячейки штатно пропущены при `run_clearml=False`.
Созданы две версии Digits/Diabetes и проверено восстановление из чистого клона.
В исходном ноутбуке путь remote заменён на `../dvc_remote`: абсолютный путь с кириллицей
вызывал ошибку кодировки при сохранении конфигурации DVC.
Выполненная копия: `../practice_3_runs/dvc_clearml_sklearn_demo.executed.ipynb`.

Ответы на вопросы ноутбука:

1. `git switch` меняет метаданные; `dvc checkout` приводит к ним файлы данных.
2. Без `dvc push` на другом компьютере могут отсутствовать сами данные.
3. Финализация закрепляет неизменяемую версию, чтобы эксперименты ссылались на одно содержимое.
4. Dataset ID указывает конкретный Dataset; поиск по имени может быть неоднозначным.
5. SHA-256 проверяет байтовое совпадение, форма и столбцы — структуру таблицы.

## Выводы

1. Состояние данных DVC задаёт содержимое `data.dvc`, прежде всего хэш директории.
   Git-коммит или tag закрепляет конкретную редакцию метаданных вместе с кодом.
2. Git хранит метаданные, а не CSV. Без доступного remote и нужных объектов в cache
   одного коммита недостаточно для восстановления.
3. ClearML version — понятный человеку номер; Dataset ID — уникальный идентификатор объекта.
4. `finalize()` закрывает текущий Dataset. Следующий создаётся отдельно с указанием parent.
5. Нужно проверить, что единственный прямой parent `2.0.0` — `BASE_ID`,
   а `WINE_ID` отсутствует среди её предков. В этой работе такая проверка пока не выполнялась.
6. Без `dvc checkout` workspace может содержать данные от предыдущей ветки.
7. DVC удобен для выполненного слияния данных вместе с Git-ветками.
   ClearML может быть удобнее для поиска версий через UI и связи с экспериментами;
   практическое сравнение будет дополнено после его запуска.
